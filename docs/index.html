Kroniki Engine

A visual novel and RPG engine: how it works and how to add content to it. React + Material UI for screens, PixiJS for the map, zustand for state. Runs as a desktop app (Electron), an Android app and in the browser, with keyboard, gamepad and touch. Play the live demo in your browser.

First steps after cloning

The game's name, ids and version are in one file, src/content/config/app.ts. Everything else (browser tab, desktop window, save folder, storage keys, save and backup formats, installers, the Android app) is filled in from it, so nothing outside src/content needs editing:

// src/content/config/app.ts
export default {
  id: 'mygame',                       // save folder, storage keys, build files
  appId: 'com.mystudio.mygame',       // store id (Android, installers)
  name: 'My Game',                    // what players see
  description: 'A small adventure',
  version: '1.0.0',                   // title screen, saves
  build: 1,                           // goes up with every release (Android needs it)
  saveFormat: 'mygame-save',          // only saves with this format load
  backupFormat: 'mygame-backup',
  iconBackground: '#0d1117',          // behind the Android adaptive icon
  splashBackground: '#000000',        // every start-up screen until the game draws
} satisfies AppConfig
  • Set id, appId and the two formats before your first release. Changing them later starts the game without the players' saves, and stores and Android treat a new appId as a different app.
  • id: letters, digits, - and _. appId: dot-separated parts that each start with a letter.
  • name may have spaces and capitals. Installer file names keep only letters, digits, spaces and . _ - ( ) ("Jack's Game" → "Jacks Game"); the window and the game show the real name.
  • Also give the title screen its name: name in src/content/titles/default/index.ts (and its translations in src/content/lang/), and the title screens' alt text.
  • The icons are files in src/content/assets/icon/: one per kind (tab and desktop, Android square, round, adaptive): see Icons and splash.

The art and sound files are stored with Git LFS, and the game doesn't build without them (the sprites' generated files are missing). With Git LFS installed, git clone gets them by itself. Without it, pnpm setup:lfs (optional) downloads Git LFS into tools/git-lfs for this repository only; then run tools/git-lfs/git-lfs pull once to fetch the files the clone left as placeholders.

How content works

All game content lives in src/content. The engine lives in src/core and you normally don't need to touch it.

  1. Make a folder with an index.ts (or .tsx) in the right place, e.g. src/content/items/potion/index.ts.
  2. Export a definition with the matching helper: export default defineItem({ … }). The helpers check your fields and give autocomplete.
  3. Use its id anywhere: game.items.add('potion'). The id is the folder name. It's typed: a typo is a TypeScript error.

A code generator (vite/registry.ts) scans the folders and writes src/generated/registry.gen.ts. It runs on its own while the dev server is up, and in pnpm typecheck / pnpm gen. You never edit generated files.

Data is written as TypeScript, not JSON, so you get autocomplete and checks everywhere. The define…() helpers do the same job as satisfies Type.

Names and groups

  • Folder names: lowercase letters, digits and _, starting with a letter (sudden_encounter_4).
  • Folders starting with _ are helpers, not entries (shared components, utilities).
  • Maps, events, windows, structures and props can be grouped: a folder without index.ts is a group. events/anna/hello/index.ts becomes the id 'anna/hello'. Up to 3 group levels.
  • Inside an entry, subfolders (art, helpers) are never scanned for more entries.

Loaded up front vs. on demand

Maps, events, windows, minigames and structures load when first used (each is its own code chunk). Characters, props, items, quests, shops, enemies, skills, troops, achievements, journal entries, gallery pictures and title screens load at start, because the engine needs their data right away.

Files that load up front must not import game (@/core/game): that creates an import loop. Use the game passed into their hooks instead (use: ({ game }) => …).

The game object

Content talks to the engine through one object. Everything on it is typed by your content.

import { game } from '@/core/game'      // or the `game` handed to hooks

game.maps.go('countryside/forest', { spawn: 'from_town' })
await game.events.start('jack/hello')
const result = await game.minigames.start('rock_paper_scissors')
game.windows.open('inventory')
game.items.add('apple', 2, { notify: true })
game.flags.set('met_anna', true)
game.quests.start('jacks_letter')
game.toast(game.t('Saved!'))

The screen stack

Screens stack as map → event → minigame → windows, with toasts on top. Only the top one gets input: while a window is open, the map doesn't move. Windows stack among themselves: opening one that is already open brings it to the front.

Conventions

  • Code style is enforced by Biome (single quotes, no semicolons, 2 spaces, 100 columns). The editor formats on save with the recommended Biome extension.
  • State lives in a few grouped zustand stores (with immer). Content reads it through game.* and React hooks like useFlag, useInventory, useGameData.
  • Things that change every frame (movement, tweens, typing text) are written straight to the screen, not through React state.
  • Hooks that may be async are typed as returning void on purpose (the engine awaits them). This avoids circular types between maps and events that refer to each other.
